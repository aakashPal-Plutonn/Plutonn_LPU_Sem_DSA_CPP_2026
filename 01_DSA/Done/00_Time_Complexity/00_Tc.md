# 1. What is an Algorithm?

An algorithm is a step-by-step set of finite, well-defined steps or instructions or rules designed to solve a problem or complete a task.

```
Think of it like a cooking recipe. Just as a recipe takes
- ingredients as input,
- follows a sequence of actions,
- and produces a finished dish as output,
an algorithm takes data, processes it through logical steps, and delivers a specific result.
```

### How Algorithms Work

Every algorithm follows a basic three-part structure: 

- **Input:** The raw data or starting materials given to the process. 
- **Process:** The clear, ordered instructions or rules applied to the data. 
- **Output:** The final result, answer, or solved problem. [1, 2]  


### Properties of an Algorithm

- Each step should be clear and unambiguous.
- Inputs should be clearly defined and specified.
- Outputs should be clearly defined and specified.
- The algorithm must terminate after finite steps.
- Each step should be feasible and executable.
- The same input should always produce the same output.
- The algorithm should be independent of language.

## Approch 1: Measuring the Running Time

A straightforward idea is to measure how long a program takes to execute.

- Means measure the manual timing using a clock/stopwatch.

**But The actual time taken by an algorithm can vary depending on the computer and its environment.**

Suppose the same algorithm is run on different machines. The measured execution time can change because of:

- Different computers
- Different clock speeds
- Different instruction sets
- Different memory access speeds

Therefore, measuring the actual clock time is **platform-dependent** and is not a reliable way to compare algorithms.

and this kind of analysis of algorithms is knows as **Posteriori Analysis**.

### Posteriori Analysis
---

**A posteriori analysis** means analyzing an algorithm **after implementation/execution** by measuring its actual running time.

**And It depends on the platform and hardware.**

> **Problem:** The same algorithm can take different amounts of time on different machines.

---

## Approach 2: Better Approach: Count Steps

Instead of measuring actual time(seconds or milliseconds) that is platform dependent, we can count the **number of basic steps/operations** performed by an algorithm.

This gives us a platform-independent way to analyze the algorithm.

### Priori Analysis
---

**A priori analysis** means analyzing the algorithm **before implementation/execution**, theoretically.

Instead of asking:

> "How many seconds does this algorithm take?"

we ask:

> "How does the number of operations grow as the input size grows?"

The general flow is:

**Step Count → Asymptotic Analysis**

---

### Example 1: Sum of Elements in an Array

Consider the algorithm:

```text
Algorithm Sum(a, n)
{
    sum = 0;

    for i = 1 to n do
        sum = sum + a[i];

    return sum;
}
```

Here:

- `a` = array
- `n` = number of elements
- `sum` = variable storing the total

**Step Count**

![Input of an Algorithm](/00_assests/TC3.png)

Therefore:
```
T(n) = 1 + (n+1) + n + 1

T(n) = 2n + 3
```

So the exact step count is:

> **T(n) = 2n + 3**

---

**Space Count**

The algorithm needs:

- 1 word for `sum`
- 1 word each for `i` and `n`
- `n` words for the array `a`

Therefore:

S(n) = n + 3

So the space requirement is:

> **S(n) = n + 3 words**

---

### Example 2: Matrix Addition

Consider:

```text
Algorithm Add(a, b, c, m, n)
{
    for i = 1 to m do
        for j = 1 to n do
            c[i,j] = a[i,j] + b[i,j];
}
```

Here:

- `a`, `b`, `c` are matrices
- `m` = number of rows
- `n` = number of columns

# 4. Asymptotic Analysis

Exact step counting can become tedious for large programs.

Imagine an algorithm containing **1000 lines of code**.

**Do we really want to calculate the exact number of steps performed by every single line?**

Can we have some bound on time complexity instead of finding exact step count?

So we want a simpler way to describe how the running time grows with input size.

**Goal:**
```
simplify the analysis of running time by getting rid of unnecessary “details”.

- like rounding: 1,000,001 ≈ 1,000,000
- 3n² ≈ n² (when focusing on growth rate)
```

> Asymptotic analysis is a technique that focuses on the significant term of a running-time expression.

> Its purpose is to capture the essence of an algorithm: how its running time increases with the size of the input.

### Example 1
```
T(n) = n^2 + n
```

For large n, n² grows much faster than n, so the n term becomes insignificant compared with n².

So we say:
> T(n) = n² + n ≈ n²

> **T(n) grows like n²**

Therefore, the asymptotic growth is described by n².
---

### Example 2
```
T(n) = 3n^2
```

The constant `3` does not change the growth rate.

So we say:
> T(n) = 3n² ≈ n²

---

### Definition

**Asymptotic analysis** is a technique used to analyze the growth of an algorithm's running time as the input size becomes large.

Its goal is to:

- Remove unnecessary details
- Focus on the **significant/dominant term**
- Describe how running time grows with input size


# 5. Asymptotic Notations

The major asymptotic notations are:

![Input of an Algorithm](/00_assests/TC5.png)

1. **Big-Oh Notation (O):**

    If f(n) describes the running time of an algorithm, then function f(n) is O(g(n)) if there exist positive constants c and n₀ (c > 0 and n₀ >= 0) such that:
    > $0 \leq f(n) \leq c \cdot g(n) \quad \text{for all } n \geq n_0$.

    This means f(n) grows no faster than g(n) multiplied by some constant for large inputs.

    It provides an upper limit on the time taken by an algorithm in terms of the size of the input. We mainly consider the worst case scenario of the algorithm to find its time complexity in terms of Big O.

    Can be used to compare the efficiency of different algorithms or data structures.

    ![Input of an Algorithm](/00_assests/TC7.png)


2. **Big Omega Notation (Ω):**

    Omega notation represents the lower bound of the running time of an algorithm. Thus, it provides the best case complexity of an algorithm.

    A function f(n) is Ω(g(n)) if there exist positive constants c and n₀ (c > 0 and n₀ >= 0) such that:
    > $0 \leq c \cdot g(n) \leq f(n) \quad \text{for all } n \geq n_0$.

    This means f(n) grows at least as fast as g(n) multiplied by some constant for large inputs.

    ![Input of an Algorithm](/00_assests/TC8.png)

3. **Big Theta Notation (Θ):**

    Theta Notation provides an exact bound on time or space complexity as it bounds a function from both upper and lower side.

    Since it represents the upper and the lower bound of the running time or space of an algorithm, it is used for analyzing the average-case complexity of an algorithm.

    A function f(n) is Θ(g(n)) if there exist positive constants c₁, c₂ (c₁ > 0 and c₂ > 0), and a natural number n₀ such that:
    > $0 \leq c_1 \cdot g(n) \leq f(n) \leq c_2 \cdot g(n) \quad \text{for all } n \geq n_0$ 
    
    This means f(n) is effectively sandwiched between c₁ ⋅ g(n) and c₂ ⋅ g(n).

    ![Input of an Algorithm](/00_assests/TC9.png)
